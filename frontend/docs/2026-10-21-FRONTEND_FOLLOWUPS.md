# 프론트 이슈 #332–335 후속 작업

1. 작업 목록은 RUNNING 우선, QUEUED는 시작 시각 오름차순으로 보여 준다. 대기 분석 앞에 실행 중 분석이 있을 때만 대기 이유를 표시한다. 초안과 분석의 큐 순번은 추측하지 않는다.
2. 후보 생성 응답과 완료 Job 결과의 cardIds를 Router state로 전달한다. 홈·목록에서 들어온 기존 카드 정렬은 유지한다.
3. 낮은 추천은 같은 목록 하단에서 기본 접는다. 검색 시 일치 항목을 자동으로 펼치며, 수동 선택·접기 후 선택·제외 복원 동작을 보존한다. 자동 추천 선택은 낮은 추천을 제외한다.
4. 요청 제한 RATE_LIMITED(429)는 GitHub Job 제한과 구분한다. 안전한 대기 시간만 안내하며 사용자의 입력과 선택을 유지하고 자동 재전송하지 않는다.

## 회귀 방지

- 기존 troubleshooting에 따라 후보 DOM 목록을 둘로 나누지 않았다.
- 공통 모바일 푸터의 레이아웃·여백은 그대로 사용한다.
- 서버 상태와 작업 결과를 추정하거나 API 필드·요청 본문을 바꾸지 않는다.
- #339 태그는 BE #338 뒤에 머지할 별도 PR로 분리한다.
- #222·#223·#224는 develop에 이미 구현된 경과 시간·재시도·사용된 후보 동작을 기존 테스트로 확인한다.

## CI에서 확인한 후속 항목

기존 멘토 단위 테스트가 NEW 후보는 모두 기본 노출된다고 가정했다. #334 요구사항에 맞춰 일반 NEW 후보 노출·낮은 추천 기본 접기·펼친 후 노출을 각각 검사하도록 변경했다. 사용된 후보의 접기·같은 목록·카드 링크 검증은 유지한다. 수정 후 관련 단위 19개가 로컬에서 통과했다. 로컬 정적 서버 시작 제한(180초) 초과는 성공으로 취급하지 않고 GitHub 전체 정적 검증을 확인한다.

## 실제 HTTP 경계 추가 검증

브라우저 Mock을 끈 `e2e-real`에서 320/1440px 작업 목록의 정렬·실행 표시·분석/초안 구분을 확인하고 캡처를 직접 점검했다. 390px 카드 확정에 429 + RATE_LIMITED + retryAfterSec=30/32400을 반환해 안내·모달 유지·본문 보존과 2.5초 뒤에도 요청이 1회뿐임을 검증했다. HTTP 검증 4개가 로컬에서 통과했다. 실제 서버에 데이터를 쓰지 않는 격리된 계약 fixture다.


## #335 최신 리뷰 — 분당/하루 한도

최신 이슈와 UserRateLimiter를 확인했다. 60초 이하는 분당 한도, 60초 초과는 서울 기준 자정까지의 하루 한도로 안내한다. 60/61/32400 경계 테스트는 기존 코드에서 실패하는 것을 확인한 뒤 수정했다. 하루 한도는 즉시 재시도를 제공하지 않는다. 잘못된 대기 시간은 안전한 기본 안내를 사용한다.

모바일 확인창에서 inline 안내와 전역 오류 토스트가 중복돼 내용을 가리는 것도 발견했다. ConfirmDialog가 오류 표시를 맡는 useConfirm에만 inline metadata를 지정해 전역 토스트를 생략한다. 인증 오류 리다이렉트는 이 검사보다 먼저 실행해 유지한다. 한도 제목을 확인창에 표시하고 하루 한도일 때 확정 버튼과 요청 함수 모두에서 반복 실행을 막는다. 다른 mutation의 알림은 유지한다.

타입 검사, 관련 단위 28개, 30초/32400초 실제 HTTP 흐름을 포함한 4개 검증이 통과했다. 모바일 안내 화면도 다시 캡처해 직접 확인했다.

### 판별 함수 타입 회귀

오류 분류 공통화 과정에서 `error is ApiError`처럼 전체 클래스를 반환 타입으로 쓰면, 이미 ApiError인 분기의 false 쪽이 never가 되어 다른 오류의 code/status 접근이 컴파일되지 않는다. 반환 타입을 `ApiError & { code: 'RATE_LIMITED' }`로 정확한 부분집합으로 좁혔다. 증분 캐시를 쓰지 않은 `tsc -b --force`와 Vite 프로덕션 빌드로 확인했다. 마지막 코드 정리 뒤에도 전체 타입 검증을 다시 수행해야 한다.
