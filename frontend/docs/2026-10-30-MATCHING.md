# 매칭 개편 — 레포별 추천 · 공고 페이지 탑 기업 · 공고 상세 매칭 · 공고에서 자소서 (흐름 확정 · API 미정)

화면 흐름과 동작 규칙만 정한 문서다. 서버 API(경로·요청·응답 칸 이름)는 아직 없고, 맨 아래 'API' 절은 비어 있다. 남은 결정('정할 것')을 정하면 그 절을 채우는 PR 을 따로 올린다. 그 전까지 지금 매칭 계약([BACKEND_CONTRACT.md](BACKEND_CONTRACT.md) '기업·직무 매칭')과 지금 화면은 그대로 둔다.

화면 설계는 이 문서로 먼저 시작할 수 있다. 칸 이름이 필요한 목(mock)은 API 절이 채워진 뒤에 만든다.

## 왜 바꾸나

- 지금은 사용자가 매칭 메뉴에 들어가야 공고를 본다. 바꾼 뒤에는 **레포 분석이 끝나면 에이전트가 그 레포에 맞는 기업을 먼저 골라 보여 준다.**
- 지금 등급(A~D)은 카드 문장과 공고 조건 문장이 '비슷한 말을 썼나' 를 재서 부정확하다. 바꾼 뒤에는 **겹친 기술처럼 사용자가 바로 확인할 수 있는 이유**를 보여 준다.
- 지금은 공고를 보고 자소서로 넘어가는 길이 없다. 바꾼 뒤에는 **공고 상세에서 바로 자소서를 시작**한다.

## 한눈에 보기

매칭은 세 곳에서, 모두 **사용자가 무언가를 끝내거나 누를 때만** 계산한다.

| 어디서 | 언제 | 무엇을 |
|---|---|---|
| ① 레포 화면 | 레포 분석이 끝날 때 | 그 레포 카드로 맞춘 기업 3곳 |
| ② 공고 페이지 | '내 조건으로 매칭하기' 를 누를 때 | 모든 레포 기록 + 인적사항으로 맞춘 탑 기업 3~5곳 |
| ③ 공고 상세 | '이 공고와 매칭하기' 를 누를 때 | 공고 하나를 조건마다 자세히 |

```
레포 분석 끝 → 그 레포 카드로 모든 공고를 맞춰 보고, 공고마다 '이 레포가 채운 조건' 을 기록
             → ① 레포 화면: 이 레포에 맞는 기업 3곳
공고 페이지 → 위: '내 조건으로 매칭하기' 결과 탑 기업 3~5곳 / 아래: 기업별 전체 공고 목록
기업·공고 → ③ 공고 상세 → '이 공고와 매칭하기' → '이 공고로 자소서 쓰기' → 자소서 ① 입력
```

## 말뜻

| 말 | 뜻 |
|---|---|
| 레포별 추천 | 레포 하나의 확정 카드로 모든 공고를 맞춘 결과. 레포 화면에 상위 기업 3곳을 보여 준다 |
| 전체 매칭 | 모든 레포의 기록과 인적사항으로 모든 공고를 맞춘 결과. 공고 페이지 위에 탑 기업 3~5곳을 보여 준다 |
| 공고 매칭 | 공고 하나를 인적사항과 카드로 조건마다 맞춘 결과. 공고 상세에 보여 준다 |
| 맞은 조건 기록 | 공고마다 '어느 레포의 카드가 어느 조건을 채웠는지'. 레포별 추천이 남기고, 전체 매칭·공고 매칭이 레포들의 기록을 합쳐 쓴다 |
| 관심 직무 | 사용자가 인적사항에서 고르는 직무 1~3개(백엔드·프론트엔드 등). 이 직무가 아닌 공고는 맞는 공고로 올리지 않는다 |
| 일반 조건 | 학력·병역·어학·자격증·근무지처럼 카드가 아니라 인적사항으로 확인하는 공고 조건(공고 조건의 `general_type`, #583) |
| 맞은 이유 | 기업·공고마다 붙는 한 줄. 예: 'Java, Spring, PostgreSQL 3개가 겹쳐요' |

## 화면

### ① 레포 화면 — 분석이 끝나면 넘어가는, 그 레포의 카드를 모아 보는 화면

카드 목록 옆이나 위에 **추천 칸**을 둔다. 자리(PC 오른쪽 칸, 모바일 카드 목록 위 등)는 FE 가 정한다.

```
이 레포 경험과 맞는 기업                                    10/30 14:20 계산
┌───────────────────────────────────────────────────────────────┐
│ [로고] 바다페이   서버 개발자(신입) · 상시 채용                  │
│        Java, Spring 2개가 겹쳐요 · 이 레포 카드 2장               │
├───────────────────────────────────────────────────────────────┤
│ [로고] 초록마켓   백엔드 개발자 · 마감 11/10                     │
│        Java 1개가 겹쳐요 · 이 레포 카드 1장                       │
├───────────────────────────────────────────────────────────────┤
│ [로고] 구름소프트  백엔드 엔지니어 · 마감 11/03                  │
│        Spring 1개가 겹쳐요 · 이 레포 카드 1장                     │
└───────────────────────────────────────────────────────────────┘
카드 1장이 확인을 기다려요. 확인하면 추천이 더 정확해져요.
모든 공고 보기 →  (공고 페이지로)
```
(회사·공고는 지어낸 예시다.)

- **이 레포의 확정 카드만으로** 고른 기업 3곳이다. 다른 레포를 분석해도 이 화면의 추천은 바뀌지 않는다.
- 기업마다 로고·이름, 대표 공고의 직무명과 마감, 맞은 이유 한 줄, 맞은 이 레포 카드 수.
- 기업을 누르면 그 기업의 대표 공고 상세(③)로 가고, 그 공고의 공고 매칭 결과가 바로 보인다.
- '모든 공고 보기' 는 공고 페이지(②)로 간다.

**화면이 그려야 할 상태**

| 상태 | 언제 | 보여 줄 것 (문구는 예시) |
|---|---|---|
| 계산 중 | 레포 카드는 다 만들어졌고 추천을 계산하는 몇 초 | '이 레포에 맞는 기업을 고르는 중이에요' |
| 추천 있음 | 위 그림 | 기업 3곳 |
| 맞는 공고 없음 | 관심 직무·인적사항에 맞는 공고가 없거나 이 레포 카드와 겹친 기술이 하나도 없음 | '이 레포와 맞는 공고가 아직 없어요' + 공고 페이지 링크 |
| 확정 카드 없음 | 이 레포 카드가 모두 확인을 기다림 | '카드를 확인하면 맞는 기업을 골라 드려요' |
| 계산 실패 | 서버 오류 | '추천을 불러오지 못했어요' + 다시 시도 |

- **확인을 기다리는 카드는 추천에 들어가지 않는다.** 문제 없는 카드는 분석 직후 자동으로 확정되므로([#568](https://github.com/kakaotechcampus-4/ktc4-kyungpook-1/issues/568)) 대부분 바로 쓰인다. 확인을 기다리는 카드가 있으면 '확인하면 추천이 더 정확해져요' 를 함께 보여 준다.

### ② 공고 페이지 — 매칭 메뉴 `/match`

위아래 두 칸이다.

```
[내 조건으로 매칭하기]                              마지막 매칭: 10/30 14:25
┌ 나와 맞는 기업 ─────────────────────────────────────────────────┐
│ [로고] 초록마켓    백엔드 개발자 · Java, React 2개가 겹쳐요          │
│ [로고] 바다페이    서버 개발자(신입) · Java 1개가 겹쳐요            │
│ [로고] 구름소프트  백엔드 엔지니어 · React 1개가 겹쳐요             │
└───────────────────────────────────────────────────────────────┘
[검색] [경력 ▾] [직무 ▾]                              기업 58곳 · 공고 629건
▸ [로고] 토스        공고 120
▸ [로고] 당근        공고 30
▸ …
```

**위: 나와 맞는 기업 (전체 매칭 결과)**
- '내 조건으로 매칭하기' 를 누르면 전체 매칭을 해서 **탑 기업 3~5곳**을 보여 준다. 기업마다 대표 공고와 맞은 이유 한 줄.
- 관심 직무·인적사항 필수 조건(학력·경력 연수 등)에 안 맞는 공고는 탑 후보에서 빠진다. **조건 때문에 뺀 기업은 따로 알리지 않는다** — 쓰는 사람이 대부분 신입이라 '지금은 못 가는 회사' 목록이 되기 쉽고, 그 기업은 아래 전체 목록에 그대로 있다.
- 기업을 누르면 대표 공고 상세(③)로 가고, 공고 매칭 결과가 바로 보인다.
- '마지막 매칭' 에 계산한 때를 적는다. 한 번도 매칭하지 않았으면 이 칸 대신 버튼과 '내 경험과 맞는 기업을 골라 드려요' 안내만 둔다.
- 그사이 바뀐 것이 없으면 **같은 결과가 나오는 것이 맞다.** 화면은 '바뀐 것이 없어 같은 결과예요' 처럼 알려 줄 수 있다. 결과가 달라지는 때: 새 공고가 들어오거나 마감됨, 레포를 더 분석함, 카드를 고치거나 더함, 인적사항·관심 직무를 바꿈.
- 계산하는 동안은 버튼을 막고 진행 표시를 한다(시간은 API 를 정할 때 잰다).

**아래: 기업별 전체 공고 목록 (둘러보기)**
- 모든 공고를 기업별로 묶어 보여 준다(기업별 보기 #545). 기업을 펼치면 그 기업의 공고가 나온다. 순서는 매칭과 상관없는 기본 순서다.
- **경력·직무 필터와 글자 검색은 이 목록에만 걸린다.** 필터를 공고에 먼저 걸고 걸러진 공고를 기업별로 묶는다(예: '신입 가능' 이면 토스는 '공고 8' 로 남고, 신입 공고가 없는 기업은 빠진다). 위의 매칭 결과는 필터와 상관없이 그대로다 — 매칭은 관심 직무와 인적사항으로만 계산한다.
- **등급(A~D)은 보이지 않는다.** 목록을 열거나 검색·필터를 바꿀 때 AI 를 부르지 않는다.

### ③ 공고 상세 — 지금 매칭 상세 화면

**열 때**: 회사·직무·마감/출처, 필수·우대 조건, 하게 될 일을 보여 준다. **계산하지 않는다.** 아래에 '이 공고와 매칭하기' 버튼을 둔다.

**'이 공고와 매칭하기' 를 누르면**: 이 공고 하나를 인적사항과 카드로 조건마다 맞춘다.
```
필수 조건
 · 4년제 대학 졸업        ✓ 인적사항과 맞아요
 · Java 개발 경험         ✓ gitory · '결제 중복 막기' 카드
   "결제 API 를 Java 로 직접 구현한 경험이 이 조건에 맞아요"     ← AI 한 줄 판단
 · Kafka 운영 경험        ✗ 맞는 카드가 없어요
우대 조건
 · AWS 배포 경험          ✓ gitory · '배포 시간 단축' 카드
```
- **일반 조건**(학력·병역·어학·자격증·근무지)은 카드가 아니라 인적사항과 비교한다. 인적사항을 적지 않았으면 '인적사항을 적으면 확인할 수 있어요'.
- **기술·경험 조건**은 맞는 카드(레포 이름 · 카드 제목)를 붙이고, AI 가 '이 경험이 조건을 채우나' 를 한 줄로 판단한다. 맞는 카드가 없으면 빈 칸으로 보여 주고 숨기지 않는다.
- 하게 될 일(담당 업무)은 판정하지 않고 지금처럼 보여 준다.
- **추천에서 들어온 경우**(① 레포 화면 3곳, ② 탑 기업 3~5곳): 이미 계산한 공고라 저장된 결과를 바로 보여 주고, 버튼은 '다시 매칭하기' 가 된다.
- 상태: 계산 중('이 공고와 내 경험을 맞춰 보는 중이에요') · 확정 카드 없음 · 계산 실패(다시 시도).

**'이 공고로 자소서 쓰기'**: 자소서 ① 입력 화면([자소서 계약](2026-10-28-COVER_LETTER.md))을 이 공고로 연다. 화면은 **공고 id 만 넘기고**, 서버가 그 공고의 회사 이름·직무·조건·하게 될 일을 자소서 AI 에 넘긴다. 문항은 사용자가 넣는다.
- AI 는 이 내용을 '공고에서 온 사실' 로 알고 써서, 사용자가 메모에 쓴 말과 섞이지 않는다. 지원 동기 문항에 회사 정보가 없던 문제도 이걸로 풀린다.
- 공고는 나중에 마감돼 사라질 수 있어서, 서버는 자소서를 만들 때 회사·조건을 자소서에 복사해 둔다. 자소서 화면에는 '토스 · 백엔드 개발자 공고로 쓴 자소서' 처럼 보여 줄 수 있다.
- 자소서 메뉴에서 바로 시작하면 공고 없이 지금처럼 쓴다.
- 자소서 API 에 공고 id(요청)와 공고 정보(응답)를 더하는 것은 자소서 계약 문서에서 정한다.

### ④ 인적사항 화면 — 관심 직무 고르기

- 인적사항([#540](https://github.com/kakaotechcampus-4/ktc4-kyungpook-1/pull/540) 의 `/settings/profile`)에 **관심 직무 1~3개 고르기**를 더한다.
- 처음에는 **카드 분야 태그로 미리 골라 둔다.** 예: 백엔드 카드가 가장 많으면 '백엔드' 가 골라져 있고, 사용자는 확인만 하거나 바꾼다.
- 고르지 않으면 직무로 거르지 않는다.
- 직무 목록은 '정할 것' 3 이다. 지금 공고 직무 분류(`BACKEND · FRONTEND · MOBILE · DEVOPS · DATA · AI_ML · SECURITY · QA · ETC`)가 출발점이다.

## 매칭하는 방법

**1단계 — 값 비교 (AI 없음)**
1. **관심 직무로 거르기** — 백엔드만 고른 사용자에게 프론트엔드·데이터 공고를 맞는 공고로 올리지 않는다.
2. **인적사항 필수 조건으로 거르기** — 학력, 최소 경력 연수처럼 공고의 **필수** 조건에 맞지 않으면 뺀다. 공고에 그런 요구가 없거나 사용자가 인적사항을 적지 않았으면 거르지 않는다.
3. **기술 겹침으로 점수 매기기** — 공고의 필수·우대 기술 목록과 카드의 기술 태그가 몇 개 겹치는지 센다. 필수 기술이 겹치면 더 높게 친다. 겹친 기술이 그대로 '맞은 이유' 가 된다.
4. 공고 점수를 기업으로 묶어 기업 순서와 대표 공고를 정한다('정할 것' 1).

**레포별 추천과 전체 매칭이 1단계를 쓰는 법**
- 레포별 추천은 그 레포 카드로 1단계를 하고, **공고마다 맞은 조건을 기록**한 뒤 상위 3곳을 보여 준다.
- 전체 매칭은 모든 레포의 기록을 공고마다 합친다. 그래서 레포마다 일부만 맞던 공고가 전체 매칭에서는 위로 올라올 수 있다.

| 공고 | 필수 기술 | 레포 A(Java) 기록 | 레포 B(React) 기록 | 전체 매칭 |
|---|---|---|---|---|
| 초록마켓 | Java, React | Java | React | **둘 다 맞음 → 1위** |
| 바다페이 | Java | Java | — | 다 맞음 |
| 구름소프트 | React | — | React | 다 맞음 |

레포 A 화면의 1위는 바다페이, 레포 B 화면의 1위는 구름소프트지만, 두 레포를 다 한 사람에게 가장 맞는 곳은 초록마켓이다. 레포 화면과 공고 페이지의 결과가 다른 것은 이 때문이고, 그게 맞다.

- 1단계는 빨라서 전체 매칭 때 새로 계산한다. 그사이 들어온 공고, 고친 카드, 바뀐 인적사항이 저절로 반영된다.

**2단계 — AI 판정**
- 상위 후보만 AI 가 '이 경험이 공고가 요구하는 깊이를 채우나' 를 판단해 순서를 다시 매긴다. 1단계 후보 안에서 순서만 바뀌어, 갑자기 전혀 다른 기업이 튀어나오지 않는다.
- 같은 카드와 같은 공고 조건에 대한 판정은 저장해 두고 다시 쓴다. 전체 매칭·공고 매칭은 새로 생긴 조합만 AI 에 묻는다.
- 맞은 이유는 AI 판단 한 줄과 근거 카드로 바뀐다. 예: '결제 대기열 장애를 직접 줄인 경험이 대용량 트래픽 처리 조건에 맞아요' + 근거 카드 제목.
- 공고 매칭은 공고 하나라 그 공고의 기술·경험 조건마다 AI 판정을 한다.
- 레포별 추천·전체 매칭에서 언제 판정할지는 '정할 것' 2 다.

## 다시 계산하는 때

| 때 | 계산 |
|---|---|
| 레포 분석이 끝나 그 레포의 카드가 다 만들어졌을 때 | 그 레포의 레포별 추천 |
| '내 조건으로 매칭하기' 를 누를 때 | 전체 매칭 |
| '이 공고와 매칭하기'·'다시 매칭하기' 를 누를 때 | 그 공고의 공고 매칭 |
| 레포 화면·공고 페이지·공고 상세를 열 때 | **하지 않는다** — 저장된 결과를 읽기만 한다 |
| 카드를 고치거나 인적사항·관심 직무를 바꿀 때 | '정할 것' 4 |

화면을 열 때 계산하지 않아서 빠르고, AI 비용도 위 세 때로 묶인다.

## 정할 것 (API 를 정하면서 하나씩)

1. 기업 점수를 정하는 법 — 추천안은 기업의 가장 잘 맞는 공고 하나로 기업 점수를 정하고, 그 공고를 대표 공고로 쓰는 것이다(공고 수가 많은 기업이 수로 밀어붙이지 않고, 이유를 '이 공고가 가장 잘 맞아요' 로 설명할 수 있다)
2. 2단계 AI 판정을 레포 분석 뒤 그 레포의 상위 후보에 바로 할지, 전체 매칭 때만 할지 — 바로 하면 레포 화면도 정확해지지만 레포마다 AI 비용이 든다
3. 관심 직무 목록과 기술 이름 목록 — 지금 카드 기술 태그는 16개라 Spring·PostgreSQL 같은 이름이 없다. 공고와 카드가 같은 목록을 쓰게 넓힌다
4. 카드를 고치거나 인적사항·관심 직무를 바꿀 때 레포별 추천·전체 매칭을 자동으로 다시 계산할지
