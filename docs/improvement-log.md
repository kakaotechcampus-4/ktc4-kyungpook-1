# 개선 기록

이 파일은 고친 문제와 숫자가 나아진 일을 서버·AI·인프라·시험 가리지 않고 모은 팀 기록이다. 항목마다 상황·원인·한 일·결과·근거 순서로 적는다. 선택지 비교는 `docs/tech-decisions.md`, 숫자 원본은 `docs/metrics-log.md` 에 있고, 여기서는 그 둘을 '문제 → 원인 → 한 일 → 결과' 이야기로 묶는다.

쓰는 규칙:
- 확인된 사실은 단정한다. 추측 말투('~할 수 있었다')를 쓰지 않는다.
- 확인되지 않은 영향(실제 사용자 불편, 재지 않은 시간)은 쓰지 않는다. 숫자는 근거(로그·PR·측정)에 있는 것만.
- 이전 코드가 있었으면 '바꿨다', 새로 만든 것이면 '만들었다·설계했다'.
- 한 일은 능동형으로 쓴다. 결과는 구체 동사(줄였다·없앴다·막았다)로 쓰고, '개선했다'는 무엇이 무엇으로 바뀌었는지와 함께만 쓴다.
- 항목 끝에 근거(PR·이슈·로그·문서)를 단다. 최신 항목이 위.

## 자소서가 문항과 상관없이 기술 문장을 옮기고 같은 이야기를 되풀이하던 것을, 문항 유형별 행동증거와 추론 표시로 바꿈 (AI·BE·FE·자소서, #719)
- 상황: 11-03 실제 카드 15장으로 가려 읽어 보니 협업 문항에 이벤트 루프·A~D 등급 같은 기술 세부가 들어가고, HTTP 카드 이야기가 세 문항에 되풀이됐으며, 재료가 없어도 상한의 70% 를 채우려 늘려 썼다. 쓰기 모델을 바꿔도(Argon·Luna·Sol, 채점용 LLM(운영 모델과 다른 모델)이 가린 비교 72표) 비겼다.
- 원인: 쓰기 지시가 '카드 사실을 빠짐없이' 와 '상한 70% 목표' 를 요구했고, 보조 카드가 다른 문항의 중심 카드와 겹쳐도 막지 않았으며, 배운 점 같은 해석을 재료 없이 썼다.
- 한 일: 문항 유형별 행동증거 4개로 쓰게 했다. 행정안전부 블라인드 채용 가이드의 채점 방식을 따랐고, IT 기업 기술 문항은 깊이를 그대로 둔다. 그 밖에 증거 수로 쓸지 정하는 준비도, 보조 카드 겹침 제거, 검토에 되풀이·문항 무관 기술 세부 추가를 만들었다. AI 가 쓴 해석에는 INFERRED 표시를 달고 확인 API·화면(확인·고치기·빼기)을 만들었다.
- 결과: 문항 사이 같은 15자 조각 11·39 → 0·0, 문장 가운데 빈칸 4·1 → 0·0, 작성 AI 추론에 숫자·영문 0(다섯 실행), 문항당 기술 이름 5~6 → 1~3, AI 시험 1,111개·BE 3,383개·FE 1,317개 통과, 되돌려 본 규칙 전부 시험이 잡음. 사용자가 어느 쪽인지 모른 채 읽은 8쌍에서 새 글 3승 · 옛 글 0승 · 새 쪽으로 기움 2 · 보류 3(10-30 같은 방식은 고친 판 0승 · 예전 판 4승). 측정 비용 약 730원.

## 되묻기 질문 상한이 3이라 네 칸을 다 묻기 전에 끝나던 것을 8로 늘리고, 계약 시험이 운영 상한을 지키게 함 (BE·되묻기, #481)
- 상황: 카드당 되묻기 질문이 3개라 네 칸(S·T·A·R)을 한 번씩도 다 묻지 못하고 끝날 수 있었고, 10-25 기술 멘토링에서 상한을 늘리라는 피드백을 받았다. 화면 예비값은 2로 서버(3)와 어긋나 있었다.
- 원인: 상한(`gitory.interview.max-turns: 3`)이 같은 칸은 두 번까지 묻는 규칙으로 닿을 수 있는 최대(네 칸 × 2 = 8)보다 작았다.
- 한 일: 상한을 8로 바꿨다(멘토 제안 10은 같은 칸을 세 번 묻게 바꿔야 해 고르지 않았다). 공유 계약 사례의 `max_turns` 를 8로 맞춰 기본 설정으로 도는 계약 시험이 운영 상한 값을 지키게 했고, 화면 예비값도 8로 맞췄다.
- 결과: 설정을 3으로 되돌리면 계약 시험 2개가 실패하는 것을 확인했다. 백엔드 전체 시험 2,918개가 통과했다.

## GitHub 이 토큰을 거절한 분석·카드 초안 실패를 일시 장애와 나눠 다시 연결을 안내함 (AI·BE·FE, #454)
- 상황: GitHub 이 토큰을 거절(401, 만료·취소)해도 분석 Job 이 `GITHUB_UNAVAILABLE`(일시 장애)로 끝나, 화면이 '다시 시도' 만 보여 줬다. 다시 시도해도 같은 이유로 실패했다. 카드 초안 도중 거절되면 카드가 '내부 오류' 로 남아 '초안 다시 만들기' 도 같은 실패를 반복했다.
- 원인: AI 가 GitHub 401 을 다른 GitHub 오류와 같은 `GITHUB_API_ERROR` 로 돌려주고, 서버는 그 코드를 일시 장애로 분류했다. 거절된 연결도 그대로 남아 `/me` 가 연결됨으로 보였다.
- 한 일: AI 가 401 을 `GITHUB_UNAUTHORIZED`(다시 시도 불가)로 나눠 주고, 서버가 그 토큰이 든 연결만 해제하게 바꿨다. 분석 Job·카드 실패 이유·초안 Job 대표 코드에 `GITHUB_UNAUTHORIZED` 를 더하고(V27), 다시 연결해야만 풀리는 실패라 대표 코드 맨 앞에 두었다. 화면 계약(`JobErrorCode`·`draftFailure`)과 다시 연결 버튼도 같은 PR 에 넣어 머지 순서에 기대지 않게 했다.
- 결과: 토큰이 거절되면 분석 실패·작업 상태·카드 화면에 '다시 연결' 이 뜨고 `/me` 의 `github.connected` 가 `false` 가 된다. 새 규칙 5곳을 되돌리면 각각 시험이 실패하는 것을 확인했다(BE 관련 패키지 1,756개·FE 402개 통과).

## 배포 서버에서 분석이 한 번도 성공하지 못하던 첫 원인을 찾아 AI 호출을 HTTP/1.1 로 고정함 (BE·운영 장애, #134)

## 로그인과 GitHub 연결 해제가 겹쳐도 해제가 지워지지 않게 연결 행을 잠그며 읽음 (BE·동시성·보안, #97)
- 상황: GitHub 연결 해제 기능을 머지하기 전, 외부 검토가 실제 Spring 트랜잭션·PostgreSQL 로 문제를 재현했다. 로그인이 연결 행을 읽은 뒤 해제가 먼저 커밋되면, 늦게 커밋되는 로그인의 UPDATE 가 해제 시각을 비우고 토큰을 다시 채웠다. 사용자는 해제 성공 응답을 받았는데 DB 는 '연결됨'이었다.
- 원인: JPA 는 바뀐 엔티티를 행 전체 UPDATE 로 쓰고, `renew()` 의 '해제된 연결은 갱신 금지' 검사도 미리 읽어 둔 값을 봐서 막지 못했다.
- 한 일: 로그인과 해제 두 곳만 잠금용 조회(`findWithLockByUserIdAndRevokedAtIsNull`, `@Lock(PESSIMISTIC_WRITE)`)로 읽어 차례로 실행되게 했다. 해제 뒤에 끝난 로그인은 새 연결로 보는 정책을 정했고, `/api/me`·수집처럼 읽기만 하는 곳은 잠그지 않았다. 바뀐 칸만 쓰는 `@DynamicUpdate` 는 CHECK `connection_revoked_has_no_token` 에 걸려 로그인 자체가 실패해 고르지 않았다.
- 결과: 실제 PostgreSQL 동시 실행 테스트 2개(로그인 중 해제 / 해제 중 로그인)를 만들었고, `@Lock` 을 빼면 두 테스트가 모두 실패하는 것을 확인했다. 마이그레이션·재시도 코드 없이 고쳤고 전체 233개가 통과했다.

## 기여 개수의 부분 실패가 0개로 저장되고 동시 저장이 서로의 칸을 덮던 문제를 머지 전에 고침 (BE·GitHub 개수 정확도·동시성, #89)
- 상황: 저장소 목록에 내 기여 개수를 넣는 PR(#89)을 리뷰하던 @taehun0208 이 두 가지를 지적했다. ① GitHub 은 일부가 실패해도 HTTP 200 으로 답하고, 실패는 errors(GraphQL)·incomplete_results(검색)로만 알린다. 그런데 이 칸을 읽지 않아 실패한 저장소가 '커밋 0개'로 저장됐고, 새 push 전까지 다시 세지 않았다. ② 분석 저장(last_analyzed_at)과 개수 저장이 같은 user_repository 행을 동시에 저장하면, 나중에 끝난 쪽이 옛 값으로 상대 칸을 덮었다(lost update).
- 원인: ① 응답의 data 만 읽고, 비어 있는 숫자를 asInt(0) 으로 0 처리했다. ② ConnectedRepository 에 @DynamicUpdate 가 없어 Hibernate 가 바뀐 칸만이 아니라 매핑된 10칸 전체를 UPDATE 했다. 두 지적을 실제 PostgreSQL 과 GitHub 응답으로 두 순서 모두 재현해 확인했다. 리뷰에 없던 문제도 찾았다. 리뷰한 PR 수에 내가 쓴 PR 이 섞이던 것이다.
- 한 일: GraphQL 오류 경로(path) 첫 칸에 적힌 저장소만 결과에서 빼고, 경로 없는 오류는 그 묶음 전체를, 덜 온 검색 결과는 이번 집계 전체를 저장하지 않게 했다. 엔티티에 @DynamicUpdate 를 넣어 바뀐 칸만 저장하게 하고, 상태 변경은 엔티티 메서드(markAnalyzed·recordCounts)로 유지했다. 개수 저장 실패도 목록 조회를 막지 않게 try/catch 범위를 넓혔다. 리뷰한 PR 수 검색어에 -author:나 를 붙였다.
- 결과: 실패한 저장소를 0개로 저장하지 않고 다음 조회 때 다시 세게 했고, 두 순서의 동시 저장 모두에서 상대 칸이 지워지지 않게 막았다(실제 PostgreSQL 테스트 2개). 리뷰한 PR 수는 팀 저장소 실측으로 @taehun0208 21 → 19, @hyukjin0324 2 → 0 으로 바로잡았다. 고친 코드를 하나씩 되돌리면 해당 테스트만 실패했고, 전체 252개가 통과했다.

## 같은 저장소를 동시에 동기화하면 가끔 실패하던 경쟁 조건을 이름 UNIQUE 제거로 없앰 (BE·동시성·DB, #81)
- 상황: GitHub 저장소 목록 동기화를 upsert(`INSERT … ON CONFLICT (github_repo_id)`)로 만들었는데도, PR 을 머지하기 전 다른 PR(#80)과 합친 전체 빌드에서 동시 동기화 테스트가 1회 실패했다(단독 6회는 통과). 에러는 `repository_owner_login_name_key` 위반이었고, 테스트의 저장소는 하나뿐이라 경쟁 말고는 설명이 되지 않았다.
- 원인: `ON CONFLICT` 는 괄호에 적은 제약만 UPDATE 로 바꿔 처리한다. 두 요청이 동시에 미리 확인을 통과하면, 지정하지 않은 `(owner_login, name)` UNIQUE 검사는 상대 커밋을 기다렸다가 바로 에러를 낸다. 저장소 이름은 GitHub 에서 바뀌고 재사용되는 값이라 사실과 맞지 않는 제약이었다.
- 한 일: 재시도나 advisory lock 대신 새 마이그레이션 V7 로 `(owner_login, name)` UNIQUE 를 지워, 남는 UNIQUE 를 `github_repo_id` 하나로 만들었다. 이 제약에 기대는 조회 코드가 없는 것을 먼저 확인했다.
- 결과: upsert 한 문장이 같은 저장소의 동시 저장을 모두 처리하게 했다. 지우고 같은 이름으로 다시 만든 저장소의 동기화가 실패하던 알려진 한계도 같이 없앴다. V7 을 빼면 `savesRecreatedRepositoryWithSameName` 이 실패하고 넣으면 통과하는 것을 로컬에서 확인했다.
- 근거: 이슈 #79 · PR #81(커밋 d5aef3b, `V7__drop_repository_name_unique.sql`), `docs/tech-decisions.md` 1번·7번

## 옛 데이터가 있는 DB 에 마이그레이션을 적용하는 시험 틀을 처음 만듦 (시험·BE 마이그레이션, #78)
- 상황: 멘토 4주차 리뷰에서 V5 가 `git_commit.exclusion_reason` 허용 목록에서 `VENDORED`·`TOO_LARGE` 를 빼면서 그 값을 가진 행을 처리하지 않은 것이 지적됐다. DB 시험은 매번 빈 DB 에 V1~최신을 적용해, '옛 데이터가 있는 DB 에 새 마이그레이션 적용' 상황을 한 번도 만들지 않았다.
- 원인: Spring 을 띄우면 Flyway 가 최신 버전까지 한 번에 적용해 중간 버전에서 멈출 수 없어, 옛 값이 든 DB 를 시험하는 틀이 없었다.
