# 프론트엔드 트러블슈팅

## 2026-09-10 — 모바일 단일 열 규칙과 데스크톱 본문 폭이 적용되지 않음

| 항목 | 내용 |
| --- | --- |
| 증상 | 모바일에서도 앱 셸이 2열처럼 계산되고, 넓은 데스크톱에서 본문이 1180px에 멈췄다. 랜딩 헤더와 본문의 시작선도 일치하지 않았다. |
| 영향 | 화면 오른쪽에 불필요한 빈 공간이 생기고 모바일 메뉴의 이름이 대부분 숨었다. 화면별 정보 우선순위가 약해졌다. |
| 확인한 사실 | `main.tsx`에서 `shell.css` 뒤에 `layout-tio.css`가 로드됐다. 뒤 파일의 `.shell`과 `.main` 규칙이 앞 파일의 모바일 미디어 쿼리와 최대 폭을 덮어썼다. |
| 조치 | 모든 기존 스타일 뒤에 `responsive.css`를 로드해 셸과 breakpoint의 최종 책임을 한 파일에 모았다. 767px 이하는 상단 브랜드와 이름이 있는 하단 메뉴, 768–1199px은 축소 사이드바, 1200px 이상은 전체 작업 폭을 사용한다. |
| 재발 방지 | Playwright가 320, 390, 768, 1024, 1440, 1920px에서 주요 라우트의 `scrollWidth`와 내비게이션을 검사한다. 새 전역 레이아웃 규칙은 `responsive.css`에 추가하고 이 파일의 로드 순서를 마지막으로 유지한다. |

## 반응형 화면 확인

```bash
cd frontend
npm install
npm run typecheck
npm test
npm run e2e
npm run e2e:static
```

브라우저에서는 최소 320px 로그인, 390px 홈·인터뷰, 768px 저장소 선택, 1024px 카드 상세, 1440px과 1920px 카드 목록을 확인한다. 고정 하단 메뉴와 화면 내부의 sticky footer가 서로 가리지 않는지도 함께 확인한다.

이번 변경에서는 2026-09-10 기준으로 타입 검사와 프로덕션 빌드가 완료됐고, Vitest 12개와 개발·정적 빌드 Playwright E2E 각각 18개가 통과했다. PC 랜딩에서는 헤더와 본문의 좌우 경계, 로고와 상단 CTA 높이의 차이를 각각 1px 이하로 검사한다.

## 보안 기록 원칙

오류 재현 자료와 문서에는 `.env`, API 키, OAuth 토큰, 세션 쿠키를 넣지 않는다. 한 번 Git 기록에 들어간 비밀은 파일을 지워도 남으므로 발견 즉시 키를 폐기하고 담당자에게 알린다.

## 2026-09-10 — 프로필 공백과 반복 카드로 정보 위계가 약함

| 항목 | 내용 |
| --- | --- |
| 증상 | 데모 사용자의 프로필이 빈 원으로 보였고, STAR가 작은 네모 네 개로만 표시되어 필드 의미와 정렬을 읽기 어려웠다. 경험·저장소·후보·통계 항목마다 둥근 카드와 그림자가 반복됐다. |
| 영향 | 중요한 제목과 상태보다 컨테이너 외곽선이 먼저 보였고, 모바일에서는 화면이 조밀하게 느껴졌다. |
| 조치 | 로컬 프로필 SVG와 오류 시 이니셜 fallback을 가진 `UserAvatar`를 공통 사용한다. STAR는 고정 네 열과 한국어 라벨을 사용한다. 반복 항목은 `experience-list`와 `record-list` 하나로 묶고 20–24px 행 간격과 구분선으로 나눈다. |
| 보존한 경계 | 선택, 확인 필요, 실패, 입력, 모달, sticky footer는 기능과 상태를 알아야 하므로 기존 경계를 유지한다. |
| 재발 방지 | Vitest가 아바타 성공·실패와 STAR 순서를 검사하고, Playwright가 목록 묶음 수, 그림자 제거, STAR 동일 너비 및 전체 breakpoint를 검사한다. |
