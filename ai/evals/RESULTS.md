# AI 품질 평가 결과

AI 작업마다 무엇을 어떻게 쟀고, 결과를 보고 무엇을 바꿨는지 모은 표다. 자세한 방법은 각 줄의 문서에 있다.
새 평가를 하면 맨 아래에 한 줄을 더하고, 같은 평가를 다시 재면 그 줄의 날짜와 숫자를 고친다.

## 다시 돌리는 곳

평가마다 측정 스크립트와 입력 세트가 있는 폴더다. 실행 명령은 각 스크립트 맨 위 설명에 있고, 모두 `ai/` 에서 돌린다.

- rn8(실제 카드, 메모 없음·있음): 두 실행 모두 협업 문항이 '멈춘 PR 이어받기' 대신 '소통 적은 팀원' 카드를 골라 기술 작업 문장 3·3 → 0·0, 저장소 작업 말(네 문항 합) 11·11 → 0·1, 코드 이름 0, 메모 있음 지원 동기는 경험 문장 4/6 → 1/4 로 줄고 포부로 맺음(검토가 경험 서술을 세 문장 돌려보낸 뒤). 문항 사이 같은 15자 조각은 0·6(메모의 '실패해도 데이터가 어긋나지 않는 백엔드' 가 지원 동기·성장 포부에 겹침). 협업 글은 카드 재료가 세 문장뿐이라 137·162자로 짧다.
- 카드 고르기 지시를 처음 고친 판(rn8a)은 두 실행 모두 여전히 '멈춘 PR 이어받기' 를 골라, 사람 이야기 기준을 fit 정의 자리로 옮기고 '팀에 알렸다·이어받았다 정도만 있는 카드는 기술 작업 카드' 를 적은 뒤 카드 고르기만 4번 돌려 3번이 사람 이야기 카드(rn8 두 실행 포함 5/6). 비용 rn8a 60.6원 · 고르기 확인 78.2원 · rn8 67.3원(합 206.1원, 태그 `cl-writer-719h`).
- rn7 vs rn8 사람 가려 읽기(`blind-read-719-r8.html`, 8쌍)는 아직 하지 않았다.

### 자소서 — 문항 첨삭
- 측정은 `gitory-eval/cover-letter/polish_measure.py`(rn8-m-1 초안을 그대로 넣고 앞뒤를 #723 검사기로 셈)이고, 4문항 × 1번이라 방향만 본다. 다섯 판 합 112.2원(태그 `cl-polish-725`).
- 첫 판에서 고친 것: ① 첫 문항(지원 동기)이 뒤 문항(성장)과 포부 구절이 겹친다고 짚혀 두 문항 모두 REPEATED 가 됐다 → 초안 검토처럼 앞 문항과 겹칠 때만 짚게 했다 ② 진단이 '전체 빌드 292개 통과' 처럼 작업량 숫자를 더 쓰라고 해 그대로 들어갔다 → 달라진 정도를 보이는 숫자만 권하게 했다 ③ 사실이 모자란 아쉬운 점마다 빈칸이 들어가 162자 협업 글이 빈칸 4줄로 쪼개졌다 → 새 빈칸은 두 개까지.
- 셋째 판은 확인 안 한 짐작 문장의 표시를 그 문장을 고쳐 쓴 자리까지 옮겨 봤는데, 문단을 통째로 다시 쓰면 사실 문장에도 표시가 붙어(지원 동기·문제 해결 문항당 4개) 그대로 남은 문장에만 옮기게 했다.
- 마지막 판에서 고친 글이 검사기에 새로 걸린 문항은 없었다(셋째 판에서는 협업 문항이 한 번 걸려 한 번 더 고쳐 씀). 다른 문항과 겹친 포부 구절은 진단이 짚어도 고쳐 쓰기가 남겼고, 성장 문항은 오히려 늘었다(15자 조각 6 → 15) — 메모의 지원 이유 문장을 옮긴 구절이다.
- 넷째 판까지는 감독 검토가 없어, 성장 문항에서 해석으로 읽히는 두 문장(배운 점·포부) 가운데 하나에만 표시가 남았다(추론 표시 7 → 4). 고쳐 쓴 짐작 문장을 쓰기 AI 가 다시 밝히지 않으면 표시가 빠질 수 있어 초안 쓰기와 같은 감독 검토를 고쳐 쓴 뒤에 붙였다. 마지막 판에서 감독이 새로 건 문장은 0개였고(성장 문항은 쓰기 AI 가 두 문장을 모두 밝혀 표시 2), 호출 하나가 늘어 문항당 약 0.8원·3초가 더 든다.

### 자소서 — 채팅으로 재료 채우기
- 측정은 `gitory-eval/cover-letter/turns_measure.py`(rn8-m-1 초안·실제 카드를 그대로 넣고, 문항마다 초안 쓰기와 같은 준비도 판단으로 재료가 보여 주는 증거와 빠진 사실 증거를 구함)이고, 빈칸이나 빠진 사실 증거가 있는 문항만 세 번씩 돌린다. 준비도 판단이 매번 조금씩 달라 문항마다 흐름 수가 다르다(성장 3 · 지원 동기 1 · 협업 1). 대본 답은 문항마다 하나씩 직접 썼고 숫자·영문 이름(N+1·JPA·API·Upgrade)을 일부러 넣었다. 네 판 합 218.8원(태그 `cl-chat-731`).
- '재료가 이미 보여 주는 증거를 물음' 은 모델이 스스로 낸 인용이 아니라 준비도 판단이 확인한 증거와 견줘 셌다. 둘째 판에서 빈칸 없는 협업 문항이 카드에 있는 행동을 한 번 되물었다(1/1) — 코드는 모델이 인용한 것만 막을 수 있어, 모델이 인용하지 않은 증거는 이 숫자로만 본다.
- 첫 판에서 고친 것: ① 충분한 답에 모델이 다음 항목을 물으려 하면(sufficient=true · ASKING) 규칙 위반으로 두 번 받다가 503 이 났다 → 충분한 답이면 코드가 FILLED 로 받게 했다 ② 꼬리 질문 말풍선이 받아 주는 말까지 네 줄이었다 → 받아 주는 말을 질문 첫 줄 앞에 붙였다(둘째 판에서 꼬리 질문을 두 줄로 줄이게 했더니 협업 문항이 두 번 다 넘겨 503 이 나서 바꿈) ③ 질문 줄 안에 예시를 또 넣었다 → 예시는 example 에만 쓰게 했다.
- 둘째·셋째 판에서 고친 것: ④ 다시 쓰기가 새 검사 문제로 바로 되돌아갔다(성장 문항 2/2 — 사용자 답의 기술 이름이 문항 상한 1개를 넘김) → 그 문제만 한 번 더 고쳐 쓰게 했다 ⑤ 그래도 기술 이름을 줄이려 다른 문장까지 바꿔 다른 문장 가드에 되돌아갔다(2/2) → 고쳐 쓰는 바퀴에 '새로 쓴 문장 안에서만 고치고 나머지는 그대로' 를 넣었다 ⑥ 빈칸 항목의 꼬리 질문을 모델이 '카드에 있다' 고 인용해 두 번 막혀 503 이 났다 → 빈칸 항목과 꼬리 질문은 인용 확인으로 막지 않게 했다.
- 마지막 판에서 남은 것: 성장 문항 1/3 이 고쳐 쓰는 바퀴에서 다른 문장을 둘 이상 바꿔 되돌아갔다(빈칸이 그대로 남고 steps 에 REVERTED). 반영된 4번은 빈칸 밖 문장을 0~1개만 바꿨다.

### 자소서 — 지원 이유 판정
- 측정은 `gitory-eval/cover-letter/memo_measure.py`(운영 코드 `judge_memo` 를 그대로 부름)이고, 메모는 실제 사용자가 쓴 '실패해도 데이터가 어긋나지 않는 백엔드를 만들고 싶어 지원한다' 를 포함해 직접 썼다. 두 판 합 18.1원(태그 `cl-reason-737`).
- 처음 판에서 틀린 4번: 공고 주요 업무 한 줄에 조건 낱말을 이어 붙이고 '경험이 있습니다' 만 더한 글(10자 조각 58%, 코드 문턱 60% 바로 아래)을 판정 모델이 3번 다 지원 이유로 봤다 — 판정 모델에 공고 회사·제목만 주고 주요 업무·조건 원문은 주지 않았다 → 원문을 함께 주고 '옮긴 문장에 자격만 덧붙인 글' 을 공고 베낌으로 적었다. 나머지 1번은 15초 안에 답을 못 받아(시간 초과) 정한 대로 쓸 수 있음으로 둔 경우다.
- 고친 판에서 공고 업무를 짚으며 왜 하고 싶은지 쓴 글('공고의 정산 업무가 제가 해 본 일과 가장 가까워서')은 3/3 지원 이유로 남았다.

### 자소서 — 카드 없는 문항의 열린 질문
- 측정은 `gitory-eval/cover-letter/open_turns_measure.py` 이고, 카드가 없는 문항에 뼈대 글(빈칸 셋)만 두고 OPEN → 상관없는 말 → 얇은 답 → 상황·행동만 든 답 → 다 든 답 순서로 같은 대화를 되돌리며 보낸다. 받은 답이 사용자가 한 말에만 기대는지는 `invented_numbers`·`unsourced_terms` 로 센다.
- 실패 문항에서 얇은 답('그냥 열심히 했어요') 한 판이 되묻지 않고 답으로 받았다(5/6). 나머지 장면은 모두 기대대로였다. 상황·행동만 보낸 답에서 '같이 정했다' 를 결과로도 받은 판이 있었는데, 결과 칸을 다시 묻지 않은 것이라 '둘 받고 결과 물음' 으로 셌다.
